# Издания и връщане назад при лоша версия

Как излиза версия: push в `main` → „Android CI“ → `auto-release.yml` → `release.yml`
публикува GitHub Release с APK, AAB и `update.json`. Инсталираните APK-та (извън
Google Play) четат `releases/latest/download/update.json` и се обновяват сами (при
отваряне — най-много веднъж на 12 ч., във фона — ~веднъж на 24 ч.). Google Play
обновява само от Play Console (AAB се качва там ръчно).

> Ръчно пусканите workflow-и (Update control, Auto release, Release): в „Run workflow“
> избери **Use workflow from: `main`**. GitHub предлага клона по подразбиране, който може
> да не е `main`; от друг клон Update control и Auto release спират с грешка, а Release
> не получава истинския ключ за подписване.

## Ако излезе лоша версия

### 1. Спри обновяванията

Actions → **Update control** → Run workflow (от `main`):

- `action`: `pause`, `tag`: `latest` (или конкретно, напр. `v1.2.7`);
- `reason`: по желание — за хората, приложението не го чете;
- `dry_run`: първо с отметка — показва новия `update.json`, без да качва нищо.

Workflow-ът добавя `"paused": true` в `update.json` на изданието и го качва наново
(`gh release upload --clobber`). Приложението тогава не предлага и не тегли тази
версия (за него е „актуално“). Вече инсталиралите я остават на нея — APK не може да
се „върне“ на по-стара версия.

> ⚠ `paused` се разбира от приложението едва от версията, в която е добавено.
> По-старите версии го пренебрегват — за тях важи т. 3 (pre-release).

### 2. Поправи напред (или върни кода)

Поправката (или `git revert` на лошите commit-и) влиза в `main` и `auto-release`
издава **нова** версия (patch +1). „Връщане назад“ винаги означава старият код,
издаден наново под **по-висока** версия: Android не инсталира обновление с по-нисък
`versionCode`, а `release.yml` го смята сам (минути от 01.01.2024), така че всяко
ново издание е по-високо — дори да е със стария код.

Новото издание качва нов `update.json` без `paused`, т.е. обновяванията тръгват
отново сами — с поправената версия. Затова докато спряната версия е последна, в
`main` да влиза само поправката: всяко друго издание от `main` също би пуснало
обновяванията (изданията само със зависимости са чернови и не влияят).

### 3. Скрий лошото издание (по желание)

В GitHub → Releases → лошото издание → Edit:

- **Set as a pre-release** — `releases/latest` вече сочи предишното издание; неговият
  `update.json` е с по-нисък `versionCode`, така че **никоя** версия на приложението
  (и по-старите без `paused`) не тегли лошата;
- или изтрий само APK/`update.json` от изданието, ако файлът не бива да се тегли и
  ръчно. Tag-ът остава — следващото издание взима по-висок номер.

### 4. Google Play

Play Console → Издание → Production (или съответната писта) → **Halt rollout**
(спиране на поетапното пускане). Новите потребители спират да получават версията;
поправката се качва като нов AAB с по-висок `versionCode` и rollout-ът продължава с
нея. Обратно към по-стар AAB в Play не може.

### 5. Пускане отново

- Поправката е издадена от `main` → нищо не трябва: новият `update.json` е без `paused`.
- Без ново издание (напр. проблемът е бил другаде) → Update control с `action: resume`
  (същият `tag`) маха `paused`.
- Ако лошото издание е маркирано като pre-release, не го връщай като „latest“ —
  следващото издание само става последно.

Промяната в `update.json` стига до приложенията при следващата им проверка
(ръчната от Настройки → Обновления е веднага; GitHub може да кешира файла няколко
минути).
